# AI 工程受控交付平台：知识治理、Harness 与 MCP 方案

> 状态：方案草案，供团队和 Claude Code 审阅补充
>
> 目标：让 AI 工程交付建立在可治理的知识、可执行的验收契约和可追溯的验证证据上；验收失败即未完成，三次修复仍失败即明确升级为输入、知识、设计或环境问题。

## 1. 结论与基本原则

这不是一个“把文档丢进向量库，再让 AI 写代码”的系统，而是一套受控交付系统：

```text
受治理知识平台
  ├─ 组织规范、领域规则、项目事实、历史经验
  ├─ 空间、权限、审计、版本、审核、归档、追溯
  └─ 统一混合检索与冲突裁决
                 ↓
任务输入 → 需求建模 → 冻结交付契约（验收标准 + 测试用例）
                 ↓
           Harness 编排 AI 开发、构建与独立验证
                 ↓
         入门禁 → 验收 → 修复循环（最多 3 次）→ 准出门禁
                 ↓
      仍失败：阻断交付，输出可追溯的失败归因与待澄清项
```

系统必须坚持以下原则：

1. **知识先治理，Agent 后接入。** 未经授权、无版本、无来源的内容不能作为强制依据。
2. **验收先冻结，开发后执行。** AI 不能在实现完成后自行定义“什么算做完”。
3. **开发与验收逻辑隔离。** 验收器只认可代码、运行产物和测试证据，不认可开发 Agent 的自我说明。
4. **结论必须有证据。** 缺少来源、版本、日志、截图或可复现结果时，结论是“未证明”，而不是“通过”。
5. **自动化有明确终点。** 同一交付契约最多三轮修复；仍失败时停止重试并升级问题。
6. **统一口径，但保留范围。** 组织规则、项目规则、任务决策的适用范围和优先级必须可判定。

## 2. 范围与非目标

### 2.1 本期范围

- 团队中心化知识库及统一治理、检索、审计能力；
- 由需求/详细设计/RAG 形成的结构化交付契约；
- 面向代码任务的 Harness 编排、门禁、三轮修复与失败归因；
- 经权限控制的 MCP 能力出口；
- 对每次交付保留知识快照、变更、验证结果和决策链路。

### 2.2 非目标

- 不以“模型自己推测业务规则”替代产品或架构决策；
- 不将原始聊天记录、未审核资料直接升级为长期事实；
- 不让 MCP 绕过权限、审计、版本或环境隔离；
- 不以无限修复循环掩盖需求歧义、知识冲突或测试环境故障；
- 不承诺 AI 在缺少可判定输入时自动产生准确验收标准。

## 3. 总体架构

```text
┌──────────────────────────── 控制平面 ────────────────────────────┐
│ 空间/身份/权限 │ 内容审核 │ 版本与归档 │ 审计 │ 策略与术语治理 │
└────────────────────────────────────────────────────────────────┘
                 │
┌──────────────────────────── 知识平面 ────────────────────────────┐
│ 原文对象库 │ 元数据与关系 │ BM25 索引 │ 向量索引 │ 重排 │ 证据引用 │
└────────────────────────────────────────────────────────────────┘
                 │ 授权、过滤、溯源的统一检索
┌──────────────────────────── 执行平面 ────────────────────────────┐
│ 需求建模器 │ 交付契约 │ Harness │ 开发 Agent │ 验收 Agent │ 门禁 │
└────────────────────────────────────────────────────────────────┘
                 │
┌──────────────────────────── 接入平面 ────────────────────────────┐
│ Web/IDE │ CI/CD │ Claude Code / Codex 等 Agent │ 受控 MCP 服务 │
└────────────────────────────────────────────────────────────────┘
```

控制平面负责“谁能看到、谁能变更、什么版本生效”；知识平面负责“什么能被可靠检索”；执行平面负责“如何交付和验证”；接入平面只消费受控能力，不能直连底层存储。

## 4. 知识对象与统一口径

### 4.1 知识分类

| 类型 | 例子 | 是否可直接约束开发 | 审核要求 |
|---|---|---:|---|
| 组织规范 | 安全、隐私、编码、发布规范 | 是 | 必须审核 |
| 项目规范 | 架构、模块边界、设计系统、接口约定 | 是 | 必须审核 |
| 领域知识 | 术语、状态机、权限、业务规则 | 视权威级别 | 必须审核 |
| 项目事实 | Schema、API、代码模块、运行环境 | 是，但有有效期 | 自动采集后需校验 |
| 经验知识 | 缺陷复盘、踩坑、排障手册 | 否，作为风险提示 | 必须审核 |
| 任务决策 | 本需求澄清、取舍、验收结论 | 仅限该任务 | 责任人确认 |
| 参考资料 | 会议纪要、外部文章、草稿 | 否 | 标明来源与可信度 |

### 4.2 每个知识对象的最小字段

```text
knowledgeId、空间、标题、类型、正文/附件、来源、作者、责任人、
权威级别、适用项目/模块/环境、状态、版本、生效时间、失效时间、
保密级别、标签、关联术语、审批记录、替代/废弃关系、内容哈希
```

任何被 Agent 用作结论依据的片段，必须能回溯到 `knowledgeId + 版本 + 片段位置`。

### 4.3 冲突裁决

同一问题命中多条知识时，优先级按以下顺序处理：

1. 法律、安全、隐私等组织强制规则；
2. 当前项目已生效的架构和领域规则；
3. 当前任务已确认的决策；
4. 已审核的经验知识；
5. 未审核参考资料。

若同级规则冲突，或适用范围无法判定，检索结果必须返回“冲突/不确定”，并阻止其作为自动开发或自动放行的唯一依据。

## 5. 空间、权限与审计

空间是权限与上下文的第一边界，至少分为组织空间、团队空间、项目空间、受限空间和任务空间。知识可以被授权引用，但不应通过复制绕过所属空间的权限规则。

### 5.1 强制控制

- 检索前先执行身份与空间权限过滤；不允许先召回再隐藏结果；
- 访问控制精确到空间、知识对象、版本及敏感字段；
- 所有创建、修改、审核、发布、归档、授权、检索、导出和 MCP 调用均记录审计事件；
- 审计事件至少包含操作者/Agent 身份、时间、空间、动作、对象版本、调用链、策略判定和结果；
- 高敏知识的检索、导出和跨空间引用需要更高权限与额外审批；
- 定期审计未使用、过期、权限过宽和长期未复核的知识。

### 5.2 密钥与隐私保护

- 入库管道进行密钥、token、密码、手机号、身份证、地址、精确位置等检测；
- 命中高风险密钥时拒绝入库，并引导写入专用密钥管理系统；
- 对允许保留的隐私字段执行脱敏，原文访问和索引访问分开授权；
- 索引、日志、提示词上下文、评估样本和导出文件都不得泄漏未授权敏感内容；
- Agent 日志只保存摘要和引用 ID，不保存完整敏感正文。

## 6. 入库审核、版本与归档

知识生命周期统一为：

```text
草稿 → 待审核 → 已生效 → 被替代 / 已废弃 → 已归档
```

- 草稿和待审核内容可检索为“参考”，不能作为强制规范；
- 已生效内容必须有责任人、审核记录、适用范围和版本号；
- 更新不覆盖旧版本；旧版本保留并标记被替代关系；
- 归档内容默认不参与普通检索，需要显式检索历史版本；
- 有效期临近或关联系统发生重大变更时，自动要求责任人复核；
- 需求、代码、测试或事故可以提交“候选知识”，但必须经过对应领域负责人审核后才进入长期记忆。

## 7. 统一混合检索

检索必须统一由知识服务执行，Agent 不能自行拼接多个库的结果。推荐流程：

```text
请求解析
  → 身份、空间、保密级别与版本过滤
  → 元数据精确过滤（项目、模块、环境、知识类型）
  → BM25 关键词召回 + 向量语义召回
  → 去重、权限复检、时效校验
  → 交叉编码器/规则重排
  → 冲突检测、证据打包、引用返回
```

BM25 负责类名、接口名、错误码、术语、版本号等精确匹配；向量检索负责自然语言语义和同义表达；重排负责把“可用、权威、适用、最新”的证据置顶。仅相似不代表可用：项目范围、版本和权威级别必须参与排序和最终判定。

返回结果至少包含：摘要、来源链接、`knowledgeId`、版本、片段锚点、适用范围、权威级别、时效状态、冲突标记和置信解释。Agent 对关键结论必须引用这些证据。

## 8. 长期记忆：只沉淀被确认的事实

长期记忆不等于聊天历史。它应分层管理：

```text
组织记忆：安全规则、工程规范、术语基线
项目记忆：架构决策、模块契约、领域规则、发布约束
任务记忆：澄清、选择、验收结果、失败归因、临时上下文
```

任务记忆随任务归档；只有经审核、具有复用价值且可证明正确的内容才能提升为项目或组织记忆。典型可沉淀对象包括：ADR、规则变更、接口契约、根因分析、测试缺口、已验证的排障手册。

每条记忆都要回答：**它是什么事实、适用于哪里、由谁确认、何时失效、替代什么、被哪些任务使用过。**

## 9. 交付契约：需求到验收的唯一桥梁

AI 不应从非结构化 PRD 直接编码。先将需求、详细设计和授权检索结果整理成版本化的交付契约，并由需求/技术责任人确认后冻结。

### 9.1 交付契约结构

```text
任务 ID、目标、范围、非范围、角色、前置条件、依赖、
业务规则、状态机、数据契约、权限与安全约束、架构约束、
验收条目（AC-*）、测试用例（TC-*）、回归范围、风险、
不确定项、知识快照、契约版本、确认记录
```

### 9.2 验收标准的硬规则

每条 `AC-*` 必须有唯一 ID，并具备前置条件、操作、输入、二值化预期结果和验证证据类型。例如“体验良好”“适当处理”“尽量快”等不可验证表述不能进入冻结契约。

每个 `AC-*` 至少关联一个 `TC-*`，并关联相应需求、架构/安全约束及最终验证证据。无法从输入中确定的业务规则必须列为待澄清项，不能由 AI 自行假设。

## 10. Harness：受控开发与独立验收编排

Harness 是一次交付的编排器，不是知识库，也不是开放式 Agent 对话。它使用冻结的交付契约和知识快照，控制任务状态、环境、工具和证据。

### 10.1 状态机

```text
Draft
  → ContractReview
  → ContractFrozen
  → Development
  → EntryGate
  → IndependentAcceptance
  ├─ Passed → ExitGate → Delivered
  ├─ Failed → Repair(1..3) → EntryGate
  └─ Blocked → Escalated
```

### 10.2 Agent 职责隔离

| 角色 | 输入 | 输出 | 禁止事项 |
|---|---|---|---|
| 需求建模 Agent | 原始需求、设计、授权知识 | 交付契约草案、澄清项 | 自行假定未定义业务规则 |
| 开发 Agent | 冻结契约、知识快照、代码库 | 代码、测试、AC 覆盖说明 | 修改验收标准以获得通过 |
| 验收 Agent | 冻结契约、实际产物、测试证据 | AC 判定、失败报告 | 信任开发 Agent 自述 |
| 归因 Agent | 连续失败的证据链 | 阻断报告、问题归类 | 再次无证据重试 |

### 10.3 门禁

入门禁确认“具备进入验收的最低质量”：构建成功、依赖/架构约束、静态检查、必需测试和安全扫描通过。

独立验收按 `AC-*` 和 `TC-*` 执行功能、边界、异常、数据、权限和回归验证。没有可复现证据的条目不能判为通过。

准出门禁确认“可交付”：所有适用验收条目通过；没有未豁免的高严重度缺陷；交付物、测试结果、知识快照和审计链完整；任何豁免均有责任人、原因、风险和到期时间。

### 10.4 三轮修复与失败归因

同一契约下最多三轮修复。每轮失败报告必须包含：

```text
AC/TC ID、失败类型、前置条件、复现步骤、预期、实际、
日志/截图/输入输出、受影响模块、根因假设、建议动作、证据链接
```

第三轮仍失败，Harness 必须停止自动开发并给出唯一或排序后的归因：实现错误、测试错误、验收定义冲突、需求缺失、知识冲突/过期、依赖不可用或环境故障。此时由相应责任人处理；修订契约或知识后，创建新版本再重新开始，不得篡改已失败运行的历史。

## 11. MCP：受控能力出口

MCP 只暴露高层、受策略控制的动作，禁止向 Agent 暴露原始数据库、任意文件系统或无审计的管理能力。

建议最小工具集：

| 工具 | 作用 | 必要控制 |
|---|---|---|
| `knowledge.search` | 返回带来源和版本的授权混合检索结果 | 权限前置过滤、结果脱敏、审计 |
| `knowledge.propose` | 提交候选知识或记忆 | 不直接生效，进入审核流 |
| `decision.record` | 记录任务或架构决策 | 责任人、范围、版本、关联任务 |
| `contract.create/update` | 创建或修订交付契约 | 冻结后需走变更流程 |
| `harness.run/status` | 启动和查看受控交付运行 | 环境隔离、任务范围、审计 |
| `evidence.query` | 查询验收、构建、测试和失败证据 | 最小权限、不可篡改引用 |

每一个 MCP 调用都要携带调用者身份、任务 ID、空间和目的；服务端负责授权、限流、脱敏、审计和版本绑定，而不是相信客户端提示词。

## 12. 评估指标与质量度量

平台上线前需要离线基准集和持续评估，至少度量：

- 检索：有用证据的召回率、精确率、过期知识命中率、冲突发现率、权限泄漏率；
- 契约：可执行验收条目占比、需求到 AC/TC 覆盖率、人工澄清率、验收条目变更率；
- 交付：首次验收通过率、平均修复轮次、三轮阻断率、缺陷逃逸率、回归率；
- 治理：审核时效、过期知识比例、无责任人知识比例、审计覆盖率；
- 效能：需求到交付周期、人工查找资料时间、重复问题复发率、人工介入质量。

任何提升“通过率”的改动都必须同时观察缺陷逃逸率，避免通过放宽验收或弱化测试制造虚假效率。

## 13. 建议落地路线

### 阶段 0：定义治理与基线

- 确定空间模型、角色、保密分级、审计保留期限和知识责任人；
- 明确组织/项目/任务规则的优先级；
- 选取一个项目和少量高价值知识类型作为试点；
- 建立检索、权限和验收的离线评估样本。

### 阶段 1：可信知识平台

- 建设知识对象模型、版本、审核、归档、脱敏和审计；
- 建设统一混合检索、重排、冲突提示和证据引用；
- 接入架构规范、设计系统、API 契约、ADR、历史缺陷和排障资料；
- 禁止未审核资料成为硬约束。

### 阶段 2：交付契约与验证基线

- 固化需求建模模板、AC/TC 模板和澄清流程；
- 将现有构建、静态检查、架构检查和测试纳入入门禁；
- 为试点任务建立独立验收器及证据格式；
- 用人工审核对照验证 AI 产出的 AC/TC 是否准确、完整、可执行。

### 阶段 3：Harness 与三轮闭环

- 以隔离环境运行开发、构建、测试和验收；
- 执行三轮上限、结构化失败报告和阻断升级；
- 将成功的决策和经确认的失败复盘提升为候选长期记忆；
- 建立交付仪表盘，持续观察质量与效能指标。

### 阶段 4：MCP 与多 Agent 接入

- 通过统一 MCP 接入 Claude Code、Codex、IDE 和 CI；
- 先开放只读检索与证据查询，再逐步开放受审核写入和 Harness 运行；
- 为不同 Agent 配置相同的规范、契约和验证出口，避免各自维护口径；
- 定期进行权限、提示词注入、数据泄漏和错误放行演练。

## 14. 需要团队确认的设计决策

以下内容不能由系统自行决定，应在落地前明确：

1. 空间层级、跨空间引用规则和各类角色权限；
2. 哪些知识类型必须人工审核，以及各自责任人；
3. 敏感信息识别、脱敏、例外审批和审计保留策略；
4. 组织/项目/任务规则冲突时的最终裁决人；
5. 哪些验收项目必须自动化，哪些允许人工证据；
