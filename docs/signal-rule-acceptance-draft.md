# 信号规则的验收项草稿（设想，尚未启用）

状态：**草稿，没有对应任务**。目前 `ResearchSignal` 全是占位数据
（`InMemoryResearchSignalRepository`），还没有真正的信号规则。等做规则的任务出现时，
用这份清单起草交付契约（`contract.create`），格式见 `platform/README.md` 的「交付契约」一节：
每条验收标准（AC-*）拆成前置条件、操作、输入、预期结果、验证方式，并至少挂一条测试用例（TC-*）。

思路来源：Simon Willison 的 Battle Drones 用 1200 场 AI 对战把"好不好玩"变成可机器判定的数字。
这里借的是"验收标准不依赖人眼"这一点，不是照搬回测。

## 假设的对象

由事件和行情产出 `ResearchSignal` 的用例（位置应在 `domain`，纯 Kotlin）。
`ResearchSignal` 当前字段：事件得分、业务相关度、近期涨跌幅、板块涨跌幅、历史相似事件数、
历史正收益占比。

## 验收项

| 编号 | 验收标准 | 验证方式 |
|---|---|---|
| AC-1 确定性 | 同一份输入（事件 + 历史日 K 线快照），连续运行两次，输出的信号列表逐字段相同 | 单元测试：固定快照，运行两次比较 |
| AC-2 不依赖当前时间和网络 | 规则计算只用传入的数据，不读系统时钟、不发请求；时间由参数传入 | 单元测试注入固定时间；Konsist 断言规则类不引用网络和时钟 |
| AC-3 数据缺失不崩 | 某只股票缺行情或 K 线不足时，该条跳过或标记缺失，不抛异常，不影响其他信号 | 单元测试：缺数据、空列表、停牌 |
| AC-4 触发数量合理 | 在一份固定的历史样本上，触发信号的数量落在契约写明的区间内，不是全触发或全不触发 | 回放测试，区间由负责人定 |
| AC-5 阈值边界 | 每个阈值（如事件得分 ≥ N）在 N-1、N、N+1 三点行为明确 | 参数化单元测试 |
| AC-6 规则改动可审核 | 改规则前后，在同一份样本上输出的差异（多了哪些、少了哪些信号）能被列出来 | 脚本对比两版输出，差异写进任务验收证据 |
| AC-7 历史统计口径 | `historicalSimilarEventCount` 与 `historicalPositiveReturnRatioPercent` 的口径写明（窗口、是否复权、分母），且不含信号出现之后才有的数据 | 测试：用截断到信号日的样本，结果与全量样本截断前一致 |
| AC-8 分层不破坏 | 规则在 `domain`，不引用 `android.*`，不调 Retrofit/Room | 现有 Konsist 断言通过 |

AC-7 最容易漏：回测里常见的错误是用了信号出现之后的数据（前视偏差）。

## 起草契约前需要负责人决定

- AC-4 的触发数量区间。
- 历史统计的窗口和复权口径。
- 固定的历史样本放在哪里、用哪几只股票、覆盖哪段时间。

## 与现有做法的对应

- AC-1、AC-3、AC-5 是普通单元测试，成本低，和 `ResolveSecurityIdUseCase` 的测试写法一致。
- AC-2、AC-8 能用现有 Konsist 机制表达。
- AC-4、AC-6、AC-7 需要一份固定的历史样本和一个输出对比脚本，可参考
  `tools/quality-baseline/` 的结构。

## 说明

这些验收项验证的是**代码行为**：规则实现得是否稳定、可复现、不看到未来。通过它们**不说明**规则对任何股票
有效，也不是投资建议。
