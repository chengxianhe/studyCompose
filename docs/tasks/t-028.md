## 第一版要回答的问题

1. 这条知识来自哪份资料、哪个版本？哪些证据支持这条关系？
2. 新指引 B 在什么适用条件下替代 A？这是谁确认的？
3. 某份来源或某条知识发生变化，哪些依赖它的知识可能需要复检？

两个验收场景：API A → API B 的技术指引更新；报销流程旧版 → 新版的非代码规则更新。
使用中文和英文夹具验证同一结构，不把结构通用性宣称为跨语言语义理解已经达标。

## 数据与语义（拟议）

继续用 SQLite 作为真源，不增加图数据库服务；ES 保持可重建检索索引职责。
节点第一版只包含现有知识对象与新增来源版本记录，不引入全套概念本体。

| 对象/关系 | 约定 |
|---|---|
| 来源版本 | 稳定来源定位符、版本标签（可未知）、内容摘要（可未知）、观察时间、登记人、许可/归属信息（可未知） |
| 知识节点 | 引用现有 knowledge_id，同时绑定 version 和 content_hash，不复制知识全文 |
| derived_from | 知识 → 来源版本；说明这条知识由哪个来源版本得来 |
| depends_on | 知识 → 前置知识；影响查询按反方向寻找依赖者 |
| supersedes | 新知识 → 旧知识；附明确适用条件和支持该替代关系的来源版本 |

来源登记必须明确为“调用方提供的观察”，不假称平台已联网抓取或验证。
有摘要时按来源与摘要去重；摘要未知时只对显式幂等请求去重，不用标题猜测同一版本。
旧来源文本保持原样，不自动冒充可验证 URI 或补造版本号；新记录独立关联。
来源版本记录不可原地覆写；纠正时新建记录，撤销错误关系并重新提案。
仅保存定位符、摘要及有界说明，不默认复制整篇外部文档；引用文本继续遵守许可要求。

每条关系有独立 ID、类型、端点快照、证据来源版本、理由、适用条件、作者、审核人与时间。
`in_review → active → revoked`；Agent 只能登记来源、提交关系与读取。
来源存在不代表内容正确；关系只有人工批准后才进入有效图，撤销保留审计记录。
审核前重新核对端点、版本、摘要和时效；端点改变不能沿用旧关系的批准。
来源标识及说明执行现有敏感信息检查；不在 URL 中保存凭据；页面展示需要转义。

拒绝未知端点、自环、同一端点快照下的重复有效关系；supersedes 拒绝形成循环。
depends_on 允许真实业务循环，查询必须以 visited 集合终止遍历。
关系审核不自动废弃旧知识、不自动改变原检索排序；不同适用条件可能同时有效。
第一版条件由人工描述并明确展示，不尝试通用版本字符串排序或自动判断条件满足。

## 查询行为与 MCP 接入（拟议）

- `graph.source_register`：登记来源版本元数据；`graph.propose`：提交关系候选。
- `graph.get/list`：读取来源、关系及待审状态，目录可见不等于可作为生效依据。
- `graph.explain`：从知识沿已审核关系追溯证据，返回路径、端点状态与适用条件。
- `graph.impact`：从来源版本反向沿 derived_from，再沿 depends_on 找潜在影响；
  从知识可直接沿反向 depends_on 查询。supersedes 仅附作替代候选，不当作依赖传播。
- MCP 不暴露人工批准/撤销工具；入口放在现有本机人工审核页。
- 默认 2 跳，最多 3 跳；返回预算最多 100 节点、200 条边，数据库读取也必须有界。
  返回稳定顺序、truncated 和截止原因，不把部分结果称为完整影响集。
- 有效证据与历史诊断分开标记：撤销/过期/端点摘要不符的关系不能成为当前有效依据；
  影响查询仍可展示已有审核历史路径并标记风险，避免知识失效后反而找不到受影响者。
- 找到路径只说明可能需要复检，不能直接宣称下游知识错误；无路径不证明完全不受影响。
- 对来源变化的判断只覆盖显式输入的两个同源版本，或用户指定的影响起点；
  不把登记时间最新当成语义版本最新，也不承诺第一版自动发现外部变化。
